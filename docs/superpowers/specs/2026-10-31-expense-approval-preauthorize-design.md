# Expense Approval API — Teaching `@PreAuthorize` the Way Teams Use It

**Status:** awaiting approval
**Date:** 2026-10-31
**Audience:** a programmer new to Java and Spring Security

## Intent

Build a small, runnable Spring Boot REST API that models an expense-approval
workflow, and use it to show how working Java teams enforce authorization with
`org.springframework.security.access.prepost.PreAuthorize`.

The point is not the expense workflow. The point is that a reader can open one
service class, see every rule for an action in one annotation, and then run a
test that proves the rule. Everything else in the project exists to make those
rules feel real: real users, real roles, real ownership, real state transitions.

## Why this shape

`@PreAuthorize` is only meaningful when the same endpoint must behave
differently for different people. An expense claim gives us three kinds of rule
that cover most real code:

- **Role rules** — only a manager may approve.
- **Ownership rules** — only the submitter may edit their own draft.
- **State rules** — nothing may be edited after submission.

It also gives a clean separation the reader should internalize: *authorization*
(who may act) belongs in `@PreAuthorize`; *business rules* (whether the action
is legal right now) belong in the service body and produce `409 Conflict`, not
`403 Forbidden`.

## Goals

1. Show `@PreAuthorize` on **service methods**, never on controllers.
2. Cover the four patterns teams actually write: role check, ownership check,
   role-or-owner check, and a named security bean in SpEL.
3. Make the difference between `401`, `403`, `404`, and `409` visible in tests.
4. Be runnable with one command on a clean Windows machine.
5. Explain each annotation in a learning guide next to the code that uses it.

## Non-goals

- User registration, password reset, email, refresh tokens.
- Pagination, sorting, search, file attachments.
- An org chart ("my manager") — managers can decide on any submitted claim.
- Multi-tenancy, audit trail, soft delete.
- A web UI, Docker, PostgreSQL, or deployment.
- Teaching OAuth2/OIDC as a protocol. JWT is used as a carrier for identity and
  roles, not as a full identity-provider integration.

## Anti-goals

These would make the project a failure even if it runs:

- Putting `@PreAuthorize` only on controllers, where it is easy to bypass by
  calling the service from another entry point.
- Hiding rules in the UI ("the button isn't shown") instead of enforcing them
  server-side.
- A role hierarchy that silently makes `ADMIN` pass every check, so the reader
  never sees the admin rule written down.
- `permitAll()` on business endpoints to make the demo easier to run.
- Tests that only check the happy path.

## Constraints

- **Java 21** toolchain; **Spring Boot 4.1.2**; **Spring Security 7**.
- **Gradle** with the Groovy DSL and a committed wrapper.
- **H2 in-memory** database, schema created and seeded at startup.
- **No Lombok** — explicit getters/constructors are easier for a Java beginner
  to follow and debug than generated code.
- Java `record`s for request/response DTOs.
- Stateless JWT (HS256) with a secret in `application.properties`.
- The development machine currently has **no JDK, Maven, or Gradle**. Before
  the first build, install Eclipse Temurin 21 via `winget`; the wrapper
  downloads Gradle itself.
- Boot 4 artifact names differ from Boot 3 (`spring-boot-starter-webmvc`,
  `spring-boot-starter-security-oauth2-resource-server`); use the names
  generated by Spring Initializr, not tutorial names.

## Approaches considered

**A. `@PreAuthorize` on service methods with a small security bean — chosen.**
Rules sit next to the business logic; ownership is expressed as
`@PreAuthorize("@expenseSecurity.canEdit(#id, authentication)")`. One place to
read, easy to test, the common team pattern.

**B. Central `PermissionEvaluator` + `hasPermission(...)`.**
Annotations become `@PreAuthorize("hasPermission(#id, 'Expense', 'EDIT')")`, with
one class mapping resource + action to rules. Scales better across many
resources, but the indirection is hard to follow while learning Java.

**C. URL-based rules only (`SecurityFilterChain` + `requestMatchers`).**
Fine for coarse gates such as "only admins reach `/api/admin/**`", but it cannot
express ownership or per-method rules. Shown briefly in a comment as the
contrast, not used for business rules.

## Domain model

**User** — `id`, `username` (unique), `passwordHash` (BCrypt), `displayName`,
`roles` (`Set<Role>`).

**Role** — enum `EMPLOYEE`, `MANAGER`, `FINANCE`, `ADMIN`.

**Expense** — `id`, `owner` (`User`), `amount` (`BigDecimal`), `currency`
(3-letter code), `description`, `status` (`ExpenseStatus`), `submittedAt`,
`decidedAt`, `decidedBy`, `paidAt`.

**ExpenseStatus** — `DRAFT → SUBMITTED → APPROVED → PAID`, plus
`SUBMITTED → REJECTED` (terminal).

Transitions, enforced in the service:

| From | To | Actor |
|---|---|---|
| DRAFT | SUBMITTED | owner |
| SUBMITTED | APPROVED | manager, admin |
| SUBMITTED | REJECTED | manager, admin |
| APPROVED | PAID | finance, admin |

Any other transition returns `409 Conflict`.

## Authorization rules

| # | Action | Endpoint | Annotation | Business check |
|---|---|---|---|---|
| 1 | Create draft | `POST /api/expenses` | `@PreAuthorize("isAuthenticated()")` | amount > 0 |
| 2 | List my expenses | `GET /api/expenses/mine` | `@PreAuthorize("isAuthenticated()")` | — |
| 3 | List all expenses | `GET /api/expenses` | `@PreAuthorize("hasAnyRole('MANAGER','FINANCE','ADMIN')")` | — |
| 4 | Read one | `GET /api/expenses/{id}` | `@PreAuthorize("@expenseSecurity.canView(#id, authentication)")` | — |
| 5 | Edit | `PUT /api/expenses/{id}` | `@PreAuthorize("@expenseSecurity.canEdit(#id, authentication)")` | status must be DRAFT |
| 6 | Delete | `DELETE /api/expenses/{id}` | `@PreAuthorize("@expenseSecurity.canEdit(#id, authentication)")` | status must be DRAFT |
| 7 | Submit | `POST /api/expenses/{id}/submit` | `@PreAuthorize("@expenseSecurity.isOwner(#id, authentication)")` | status must be DRAFT |
| 8 | Approve | `POST /api/expenses/{id}/approve` | `@PreAuthorize("hasAnyRole('MANAGER','ADMIN')")` | status must be SUBMITTED |
| 9 | Reject | `POST /api/expenses/{id}/reject` | `@PreAuthorize("hasAnyRole('MANAGER','ADMIN')")` | status must be SUBMITTED |
| 10 | Mark paid | `POST /api/expenses/{id}/pay` | `@PreAuthorize("hasAnyRole('FINANCE','ADMIN')")` | status must be APPROVED |
| 11 | List users | `GET /api/admin/users` | `@PreAuthorize("hasRole('ADMIN')")` | — |

`ExpenseSecurity` (bean name `expenseSecurity`) exposes:

- `boolean isOwner(Long expenseId, Authentication authentication)`
- `boolean canView(Long expenseId, Authentication authentication)` — owner, or
  `MANAGER` / `FINANCE` / `ADMIN`
- `boolean canEdit(Long expenseId, Authentication authentication)` — owner only

The bean returns `false` when the expense does not exist, so a stranger probing
IDs gets `403`, not a `404` that confirms the row exists. That means `404` is
reachable only where the role check passes before the service loads the row:
`approve`, `reject`, `pay`, and the admin user listing. Tests pin both cases —
`employeeReadingMissingExpenseReturns403` and
`managerApprovingMissingExpenseReturns404` — and the guide explains the
trade-off between hiding existence and reporting it accurately.

State checks are **not** in annotations. A manager approving an already-approved
claim passes `@PreAuthorize` and gets `409` from the service. The guide explains
why: the annotation answers "may this person act on this resource", the service
answers "is this action legal now".

## API shape

- `POST /api/auth/login` — `{ "username", "password" }` → `{ "token", "expiresIn",
  "roles" }`; `401` on bad credentials. Public.
- Expense DTOs: `ExpenseRequest { amount, currency, description }`,
  `ExpenseResponse { id, owner, amount, currency, description, status,
  submittedAt, decidedAt, decidedBy, paidAt }`. `owner` and `decidedBy` are
  usernames (`String`), not nested user objects, so responses never expose
  password hashes or trigger lazy-loading.
- `GET /api/admin/users` returns `List<UserResponse>` where
  `UserResponse { id, username, displayName, roles }`. `passwordHash` is never
  serialized.
- Success statuses: `POST /api/expenses` → `201` with body and a `Location`
  header; `PUT` and all four transitions → `200` with the updated
  `ExpenseResponse`; `DELETE` → `204` with no body; login → `200`.
- Input validation uses Bean Validation on `ExpenseRequest`
  (`@Positive amount`, `@NotBlank description`, `@Pattern` for a 3-letter
  currency) and produces `400`. Because request-body validation runs before the
  controller calls the service, an invalid body sent by a non-owner returns
  `400` rather than `403`; the guide calls this ordering out explicitly.
  `amount <= 0` is therefore validation (`400`), never `409`.
- Errors: JSON `{ timestamp, status, error, message, path }`.
  - `401` — missing, malformed, or expired token (from the bearer entry point).
  - `403` — authenticated but not allowed (from the access-denied handler).
  - `404` — authorized, but the row is gone.
  - `409` — illegal state transition.
  - `400` — validation failure, with field messages.

## Security configuration decisions

- `@EnableMethodSecurity` on the config class; `prePostEnabled` is on by default
  in Spring Security 7.
- Filter chain: CSRF disabled, session creation `STATELESS`, `/api/auth/login`
  and `/error` permitted, everything else authenticated.
- JWT: HS256 with a 256-bit secret from `app.jwt.secret`; 60-minute expiry;
  claims `sub` (username), `roles` (list of `ROLE_*` strings).
- `JwtAuthenticationConverter` reads the `roles` claim and maps each value
  directly to a `SimpleGrantedAuthority` (no `SCOPE_` prefix).
- Login is a plain service method: load user by username, `passwordEncoder.matches`,
  then encode a token. No `AuthenticationManager`, no `UserDetailsService` — fewer
  moving parts, same outcome, and the guide can explain each line.
- `PasswordEncoder` is `BCryptPasswordEncoder`.

## Testing strategy

`./gradlew test` must pass from a clean checkout.

- `ExpenseAuthorizationTest` — `@SpringBootTest` + `@AutoConfigureMockMvc`,
  one test per rule in the table, named for the rule
  (`employeeCannotApprove`, `managerCanApproveSubmitted`, ...). Asserts the exact
  status and, for allowed cases, the resulting state.
- **Test isolation:** each test class is `@Transactional` so every test rolls
  back, and each test creates its own users and expenses through the
  repositories in `@BeforeEach` instead of mutating the seed rows. The seeder
  exists for `requests.http` and manual exploration; tests never depend on it.
  This keeps the suite independent of execution order and of Spring's cached
  application context.
- `ExpenseSecurityTest` — plain unit test of the ownership bean: owner, stranger,
  manager, missing ID.
- `AuthTest` — login success returns a usable token; wrong password is `401`;
  no token on a protected endpoint is `401`; a token signed with the wrong key
  is `401`.
- `ExpenseStateTest` — `409` cases: edit after submit, approve twice, pay before
  approval.
- Test helper `TestTokens` mints tokens with the application's `JwtEncoder`, so
  tests do not depend on the login endpoint except in `AuthTest`.

## Decisions made on the reader's behalf

- No Lombok.
- One role per seeded user, but the model supports several.
- Managers decide on any submitted claim; no org chart.
- 403 for unknown IDs on ownership-checked endpoints (no existence leak).
- `ADMIN` is written explicitly in each rule instead of inheriting every role.
